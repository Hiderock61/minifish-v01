# 明智工務店・方法©️ → Codex 実行 Skill v0.1

## 基本
人間は発想と最終判断。Codexは調査・設計・施工・検査を担当。方法©️は単なる専門家ロールプレイではなく「目的→分解→既存装置→最小施工→実証→監査」の工程。

## 0. 正本を先に確認
- 作業対象の README、関連 Issue、実コード、検査結果を読む。
- 方法の再現が必要なら、公開設計図 `https://github.com/Hiderock61/hiderock-method-os` の README.md → METHOD_HOME.md → RECOVERY.md → 対象方法本文の順に確認する。本館 `https://github.com/Hiderock61/hiderock61.github.io/tree/main/methods` も確認できる範囲で参照。
- Notion の運用正本が利用可能な場合は最新の内容を優先する。利用権限がなければ読めたふりをせず、GitHub側で確認できた範囲を明示する。
- 「それってどうやるの法©️」と「それってどう作るの法©️」の詳しい手順を想像で補わない。正本が不足したら、取得できた内容と不足分を報告する。

## 1. HOWTO（どうやるの）
目的、入力、出力、具体的な動詞、既存条件、外部制約、完成判定を確定する。技術者・利用者・品質・安全・費用などの観点を必要に応じて切り替え、矛盾・欠落を調査する。複数人格を演じるだけで済ませない。

## 2. BUILD（どう作るの）
①既存の完成形を紙芝居として具体化 → ②必要部品へ分解 → ③既存の実証済み部品を優先再利用 → ④最小変更で施工 → ⑤安全な実動作で証拠取得 → ⑥検査・監査。未取得・未検証の結果を成果として扱わない。

## 3. MiniFish 施工境界
- まず内部デモや既存モックでの再現とユニットテストを行う。必要に応じて、依存関係が準備できた環境で `PYTHONPATH=. pytest -q` 等の既存テストを実行。
- 一度の依頼で安全に完結できる実装・検査はまとめて行い、途中の細かなボタン操作を人間に返さない。
- 実Webへのアクセス・Secret利用・API実通信・課金・公開・削除・応募・購入などは個別許可がなければしない。
- GitHub Issue コメントによる既存の自動実行トリガーを無断で起動しない。
- 複数作業を並行するときは、競合するファイルを同時変更しない。

## 4. 帰還形式
1. 現在地（PROVEN / UNKNOWN / BLOCKED）
2. 変更ファイルとその理由
3. 実際に行ったテスト、実測の結果
4. 人力で省略できた工程
5. 未検証・費用・外部接続の境界
6. 次に人間の判断が必要なことだけ、平易な日本語で報告

## ルール
- 誰かの「プロの気持ち」を演じただけで独立監査済みと主張しない。
- 安全でない実行を先回りして勝手に承認しない。
- 要件があれば理由を述べ、作業を中断する。自動実行できない理由も具体的に報告する。
